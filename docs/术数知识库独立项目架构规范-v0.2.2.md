# 术数知识库独立项目架构规范 v0.2.2

## 1. 项目定位

当前知识库作为一个**独立项目**开发和测试。

测试阶段：

- 不挂接龟甲。
- 不修改龟甲现有代码。
- 不依赖八字、六爻模块。
- 可以独立启动、浏览、测试和构建。
- 保留稳定的对外接口，为未来接入龟甲或其他前台做准备。

核心原则：

> 知识库本身是一套独立的知识基础设施，任何前台都只是它的消费者。

---

## 2. 技术分层

整体划分为：

```text
知识内容
    ↓
知识结构定义
    ↓
加载 / 校验 / 注册 / 关系解析
    ↓
公开 API
    ↓
独立知识库前台
    ↓
未来：龟甲 / 其他前台
```

依赖方向只能向下。

禁止：

```text
knowledge-core → 页面组件
knowledge-core → 龟甲
knowledge-core → 八字
knowledge-core → 六爻
```

允许：

```text
独立前台 → knowledge-core
龟甲 → knowledge-core
其他应用 → knowledge-core
```

---

## 3. 内容与程序分离

一个知识点可以拆成多个正文 section。

`entry.ts` 负责机器可读信息：

- ID
- 名称
- 分类
- 别名
- 摘要
- section 顺序
- 关系
- 来源引用
- 状态

Markdown 负责正文。

修改某一知识层级时，应尽量只修改对应 section，不牵动其他内容。

---

## 4. 永久 Knowledge ID

每个知识条目必须拥有稳定 ID，例如：

```text
wuxing.wood
tiangan.jia
dizhi.zi
shishen.zhengguan
```

规则：

1. ID 一旦正式使用，原则上不再修改。
2. 页面标题可以修改。
3. 显示名称可以修改。
4. URL 可以修改。
5. 分类结构未来可以调整。
6. 外部程序永远优先通过 ID 引用知识。

Knowledge ID 是跨系统稳定接口。

---

## 5. URL 不属于知识核心

Knowledge ID 属于知识本身。

URL 属于具体前台。

例如同一个：

```text
tiangan.ding
```

独立知识库可以路由为：

```text
/knowledge/tiangan/ding
```

未来龟甲可以路由为：

```text
/kb/tiangan/ding
```

正文和知识核心不应依赖具体 URL。

---

## 6. 分类、条目和关系类型都是数据

禁止在页面业务逻辑中硬编码：

```ts
if (category === 'wuxing')
```

分类应独立声明。

条目、分类、关系类型通过自动发现机制注册。

新增知识点原则上只增加数据文件和正文文件，不要求修改：

- 中央条目列表；
- 路由表；
- 首页；
- 导航栏；
- Registry。

---

## 7. Registry 是内部唯一可信索引

Registry 负责：

```text
Knowledge ID → Entry
Category ID → Category
Relation Type → Relation Definition
```

其他模块不得自行扫描文件建立第二套索引。

---

## 8. Validator 在开发阶段发现错误

加载后立即检查：

- Knowledge ID 是否重复；
- slug 是否重复；
- categoryId 是否存在；
- section source 是否存在；
- relation target 是否存在；
- relation type 是否存在；
- 正文引用的 Knowledge ID 是否存在；
- source ID 是否存在。

死链接不能等用户点击后才发现。

---

## 9. 一个知识事实尽量只维护一次

同一个机器事实不得同时在多处独立手工维护。

例如：

```text
甲与己合
甲禄在寅
甲刃在卯
```

如果已经作为结构化事实存在，正文可以解释或展示，但程序不应再要求维护第二份相同事实数据。

核心原则：

> 正文负责解释，结构化数据负责机器事实。

---

## 10. Knowledge Relation

正文中的：

> 木生火。

是给人阅读的文字。

机器关系应使用：

```ts
{
  type: 'wuxing.generates',
  target: 'wuxing.fire'
}
```

关系类型独立定义，不硬编码在组件中。

---

## 11. 关系事实只维护一个方向

例如：

```text
木 → 火
```

只维护：

```text
木生火
```

反向：

```text
火受生于木
```

由 backlinks 自动生成。

不得要求两个条目各自手工维护同一关系。

---

## 12. 正文知识引用使用稳定 Knowledge ID

显式引用采用：

```text
[[wuxing.wood|木]]
```

而不是写死 URL。

解析后前台再根据当前 Route Adapter 生成实际页面地址。

---

## 13. 概念链接分为“可链接能力”和“编辑呈现”

是否存在可导航知识目标，由：

```text
Knowledge ID + Registry
```

决定。

正文编辑者不应因为某一处忘记手写链接，就导致同一概念在不同位置表现不一致。

---

## 14. 概念自动链接规则

概念链接遵循以下规则：

1. 显式 `[[id|文本]]` 优先，用于精确指定目标和消歧。
2. 普通正文中，只要 Registry 已存在无歧义的目标条目，可自动链接其首次普通出现。
3. 当前条目自身不自动自链。
4. **普通正文与列表以 section 为去重范围。**同一 section 内，同一个 Knowledge ID 原则上只在正文或列表中自动链接一次。
5. **视觉强调本身不构成链接保护条件。**普通正文中的加粗、斜体等格式仍可在保持原有视觉样式的前提下识别和生成概念链接。
6. **文献原文引用属于证据层，不参与概念自动链接。**引用原文中的天干、地支、五行、十神等词语即使已经拥有 Knowledge ID，也保持原文，不插入自动链接。
7. 文献原文的保护依据必须是明确的语义标记，例如文献引用组件、原典引用字段或 Markdown blockquote；**不能仅凭中文引号“……”判断为文献原文**。正文中用于解释术语的引号仍按普通正文处理。
8. 原典引用中原则上也不主动书写显式知识链接，避免改变证据文本的阅读连续性。若需要解释其中概念，应在引用文之外的解释正文中建立链接。
9. 标题、代码及其他不应被正文解析器改写的结构继续保持保护。
10. **表格采用独立于正文的结构化链接规则。**只有当整个单元格的可见文字恰好等于一个无歧义知识概念名称时，才自动生成链接；不得因为单元格中包含某个概念词而对子字符串自动加链接。例如“同五行”“五行生克”不会仅因包含“五行”而自动链接。
11. 表格链接不受同一 section 正文此前是否已链接该 Knowledge ID 的影响，正文中的链接也不因表格已经链接而被消耗。
12. **同一张表格内部，同一个 Knowledge ID 原则上只自动链接一次。**不同 Knowledge ID 可以分别链接。
13. 同名词若对应多个 Knowledge ID，程序不得猜测，必须显式指定 ID。

---

## 15. 条目尚未存在时不制造假链接

如果正文出现：

```text
寅
比肩
十二长生
```

但 Registry 中尚无对应独立条目，则保持普通文本。

未来相应条目建立后，已有正文可以自动获得链接能力，而不要求逐篇回头补 Markdown。

---

## 16. 显式链接用于精确控制和消歧

自动链接解决“已有概念是否可导航”的一致性。

显式链接解决：

- 同名歧义；
- 显示文字与标题不同；
- 需要明确指定目标；
- 编辑者希望固定某一处为主要概念入口。

两者并存，不互相替代。

**文献原文引用是例外。**证据文本以保持原文连续性为优先，不把显式知识链接作为原文标注手段；需要导航时，应在引用文之外的解释正文中建立链接。

---

## 17. 结构化关系优先于正文手工关系

像以下事实：

- 五行生克；
- 天干五合；
- 同五行阴阳配对；
- 禄；
- 羊刃；

如果属于稳定、可机器表达的事实，应逐步进入结构化数据或 Relation 系统。

页面可以继续以自然语言展示，但不应要求正文重复承担机器事实维护责任。

---

## 18. 可计算结论不重复手工维护

例如十神映射由：

- 日干；
- 五行生克；
- 阴阳异同；

共同决定。

页面可以展示完整结论表，但底层原则上应由统一规则或统一事实数据生成，而不是十个天干各自维护十张互不关联的静态表。

专项知识条目负责解释规则；天干条目只负责展示当前天干的结论。

---

## 19. 来源系统独立管理

经典文献会被大量重复使用，来源本身不应在每个条目重复录入。

正文或 section 只引用稳定 source ID 和 locator。

以后修改版本、书名、作者、卷次信息时，只修改来源目录。

---

## 20. public API 是外部唯一入口

外部消费者不得直接导入某个条目文件。

统一通过 public API：

```ts
getEntry(id)
getEntriesByCategory(categoryId)
getRelations(id)
getBacklinks(id)
resolveKnowledgeReference(id)
searchKnowledge(query)
```

未来龟甲只依赖 public API 和 Knowledge ID。

---

## 21. 搜索与链接不是同一机制

搜索负责：

- title
- aliases
- summary
- 未来全文索引

概念链接负责：

- 已知知识之间的稳定导航；
- ID 解析；
- 关系跳转。

不得用搜索结果临时猜测链接目标。

---

## 22. 自动化测试与审计

至少覆盖：

### Registry

- 自动发现全部 entry；
- ID 唯一；
- 分类正确。

### Validator

- 重复 ID 失败；
- 不存在 category 失败；
- 不存在 relation target 失败；
- 不存在 section 失败；
- 不存在 Knowledge ID 引用失败。

### Relation

- 正向关系存在；
- 反向 backlinks 自动生成；
- 不要求双向手工录入。

### Link Resolver

- 显式 Knowledge ID 引用可解析；
- 已存在、无歧义概念可自动链接；
- 当前条目不自链；
- 普通正文与列表在同一 section 内不重复自动链接；
- 普通加粗、斜体不阻断概念自动链接；
- 文献原文引用不参与自动链接；
- 中文引号本身不被误判为文献原文保护标记；
- 表格只对完整单元格概念名自动链接，不对子字符串自动链接；
- 表格链接范围独立于正文 section 去重；
- 同一表格内同一 Knowledge ID 不重复自动链接；
- 歧义概念不自动猜测；
- 新增目标条目后旧正文可获得链接能力。

### Navigation

- 分类页可直达；
- 详情页可直接 URL 访问；
- Route Adapter 与 Knowledge ID 解耦。

### Static Audit

静态审计不得硬编码：

- 固定条目数量；
- 固定某一分类只有若干条目；
- 必须手工更新中央列表。

审计应检查结构规则，而不是冻结当前数据规模。

---

## 23. 当前阶段仍禁止的事项

暂时不要加入：

- AI 自动解释；
- 用户编辑系统；
- 后台 CMS；
- 复杂全文搜索；
- 收藏；
- 阅读历史；
- 账号体系；
- 龟甲排盘联动；
- 八字判断逻辑；
- 六爻判断逻辑。

这些不是知识核心当前任务。

---

## 24. 最终原则

> 内容与程序分离。

> 一个文件尽量只承担一种职责。

> 一个知识事实尽量只维护一次。

> Knowledge ID 是跨系统稳定接口。

> URL、页面和视觉形式都不是知识本身。

> 正文负责解释，结构化数据负责机器事实。

> 是否能够链接由 Knowledge ID 与 Registry 决定。

> 自动链接不得猜测歧义概念。

> 文献原文属于证据层，不参与概念自动链接。

> 视觉强调不是链接保护条件；正文链接去重以 section 为边界，表格采用独立的完整单元格链接规则。

> 测试阶段知识库完全独立存在。

> 龟甲未来可以使用知识库，但知识库不依赖龟甲。
