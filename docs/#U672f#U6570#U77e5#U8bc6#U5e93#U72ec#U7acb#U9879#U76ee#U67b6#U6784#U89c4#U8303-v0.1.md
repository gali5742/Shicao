# 术数知识库独立项目架构规范 v0.1

## 1. 项目定位

当前知识库作为一个**独立项目**开发和测试。

测试阶段：

- 不挂接龟甲。
- 不修改龟甲现有代码。
- 不依赖八字、六爻模块。
- 可以独立启动、浏览、测试和构建。
- 保留稳定的对外接口，为未来接入龟甲或其他前台做准备。

核心原则：

> 知识库本身是一套独立的知识基础设施，任何前台都只是它的消费者。

---

# 2. 技术分层

整体划分为：

```text
知识内容
    ↓
知识结构定义
    ↓
加载 / 校验 / 注册 / 关系解析
    ↓
公开 API
    ↓
独立知识库前台
    ↓
未来：龟甲 / 其他前台
```

依赖方向只能向下。

禁止：

```text
knowledge-core → 页面组件
knowledge-core → 龟甲
knowledge-core → 八字
knowledge-core → 六爻
```

允许：

```text
独立前台 → knowledge-core
龟甲 → knowledge-core
其他应用 → knowledge-core
```

# 4. 为什么正文不全部放进 entry.ts

一个知识点虽然应该独立，但一个知识点内部也可能不断增长。

例如“木”未来可能包含：

```text
基本定义
基本性质
方位
季节
生克
阴阳
与天干关系
与地支关系
经典文献
命理中的使用
延伸理解
```

如果全部放入：

```text
wood.ts
```

最终仍然会变成几百甚至上千行的大文件。

因此采用：

```text
wood/
├─ entry.ts
├─ basic.md
├─ characteristics.md
├─ season.md
└─ extensions.md
```

其中：

**entry.ts**

只负责机器可读取的信息：

- ID
- 名称
- 分类
- 别名
- 摘要
- section 顺序
- 关系
- 来源引用
- 状态

Markdown 文件只负责正文。

这样修改“四时中的木”，只需要修改：

```text
season.md
```

而不用动其他部分。

# 5. 永久知识 ID

每个知识条目必须拥有稳定 ID。

例如：

```text
wuxing.wood
wuxing.fire

tiangan.jia
tiangan.yi
tiangan.ding

dizhi.zi
dizhi.hai

shishen.zhengguan
shishen.shangguan
```

规则：

1. ID 一旦正式使用，原则上不再修改。
2. 页面标题可以修改。
3. 显示名称可以修改。
4. URL 可以修改。
5. 分类结构未来可以调整。
6. 外部程序永远优先通过 ID 引用知识。

例如龟甲未来只需要知道：

```text
tiangan.ding
```

而不需要知道“丁”这个页面具体存在哪里。

# 6. KnowledgeEntry 第一版结构

建议：

```ts
export interface KnowledgeEntry {
  id: string

  categoryId: string

  slug: string

  title: string

  aliases?: string[]

  summary?: string

  sections: KnowledgeSectionReference[]

  relations?: KnowledgeRelation[]

  citations?: KnowledgeCitation[]

  status?: 'draft' | 'review' | 'published'
}
```

其中：

```ts
export interface KnowledgeSectionReference {
  id: string
  title: string
  source: string
}
```

例如“木”：

```ts
export default {
  id: 'wuxing.wood',

  categoryId: 'wuxing',

  slug: 'wood',

  title: '木',

  aliases: ['木行'],

  summary: '五行之一。',

  sections: [
    {
      id: 'basic',
      title: '基本概念',
      source: './basic.md'
    },
    {
      id: 'characteristics',
      title: '基本性质',
      source: './characteristics.md'
    },
    {
      id: 'season',
      title: '四时',
      source: './season.md'
    }
  ],

  relations: [],

  status: 'draft'
} satisfies KnowledgeEntry
```

# 7. 分类本身也是数据

不要在页面里：

```ts
if (category === 'wuxing')
```

然后手写“五行”。

分类应独立声明，例如：

```ts
{
  id: 'wuxing',
  title: '五行',
  description: '...',
  order: 10
}
```

以后增加：

```text
十神
十二长生
神煞
六亲
六十四卦
```

原则上都只增加数据文件。

前台根据 Category Registry 自动生成分类。

# 8. 知识关系

正文中的：

> 木生火。

只是给人阅读的文字。

机器还需要知道：

```ts
{
  type: 'wuxing.generates',
  target: 'wuxing.fire'
}
```

因此关系采用：

```ts
export interface KnowledgeRelation {
  type: string
  target: string
  note?: string
}
```

例如：

```ts
relations: [
  {
    type: 'wuxing.generates',
    target: 'wuxing.fire'
  },
  {
    type: 'wuxing.controls',
    target: 'wuxing.earth'
  }
]
```

---

# 9. 关系类型本身也独立定义

不要把：

```text
generates = 生
controls = 克
```

硬编码进 RelationList.vue。

建立：

```text
relation-types/
├─ generates.ts
└─ controls.ts
```

例如：

```ts
{
  id: 'wuxing.generates',

  label: '生',

  inverseId: 'wuxing.generatedBy',

  inverseLabel: '受生于',

  directed: true
}
```

这样前台不需要理解什么叫“生”。

前台只负责问：

```text
这个 relation type 应该显示什么？
```

---

# 10. 关系只维护一次

例如：

```text
木 → 火
```

只在“木”中声明：

```ts
{
  type: 'wuxing.generates',
  target: 'wuxing.fire'
}
```

禁止再要求 `fire/entry.ts` 手工写：

```text
火受生于木
```

运行时由：

```text
backlinks.ts
```

自动生成反向关系。

因此数据库只有一个事实：

```text
木生火
```

程序自动推导：

```text
火受生于木
```

避免两边内容失配。

---

# 11. 条目内部链接

正文需要支持知识 ID 引用。

第一版可以使用：

```text
[[wuxing.wood|木]]
```

例如：

```text
甲为阳[[wuxing.wood|木]]。
```

解析后前台显示：

```text
甲为阳木。
```

其中“木”可点击。

同样：

```text
[[shishen.shangguan|伤官]]
```

以后无论 URL 如何变化，正文引用仍然有效。

# 12. 自动发现条目

禁止建立这种中央维护列表：

```ts
import wood from './wood'
import fire from './fire'
import earth from './earth'

const entries = [
  wood,
  fire,
  earth
]
```

加载器通过：

```ts
import.meta.glob()
```

自动发现：

```text
entries/**/entry.ts
```

分类：

```text
categories/*.ts
```

关系类型：

```text
relation-types/*.ts
```

也采用相同方式自动注册。

因此添加一个新知识点时，原则上只需要：

```text
新增目录和文件
```

而不需要再修改：

```text
总列表
路由表
首页
导航栏
Registry
```

---

# 13. Registry

Registry 是内部唯一可信的数据索引。

负责：

```text
ID → KnowledgeEntry
Category ID → Category
Relation Type → Relation Definition
```

基本能力：

```ts
getEntry(id)

getCategory(id)

listEntries()

listEntriesByCategory(categoryId)

hasEntry(id)
```

其他程序禁止自行扫描文件。

---

# 14. Validator

加载完成后立即进行一致性检查。

至少检查：

```text
知识 ID 是否重复
slug 是否重复
categoryId 是否存在
section source 是否存在
relation target 是否存在
relation type 是否存在
引用的知识 ID 是否存在
source ID 是否存在
```

例如：

```text
甲 → wuxing.wood
```

但：

```text
wuxing.wood
```

不存在，则开发阶段直接报错。

不能等用户点击之后才发现死链接。

---

# 15. 来源系统

经典文献以后会大量重复使用，因此来源本身不应该在每个条目重新输入。

例如建立：

```text
sources/
├─ dili-tiansui.ts
├─ sanming-tonghui.ts
└─ yuanhai-ziping.ts
```

正文或 section 只引用：

```ts
{
  sourceId: 'book.ditian-sui',
  locator: '某卷某章'
}
```

这样以后修改版本信息，只需要修改来源目录。

第一阶段来源系统可以很简单，但结构从一开始保留。

# 16. public-api.ts

这是未来所有消费者唯一应该依赖的入口。

第一版建议暴露：

```ts
getEntry(id)

getEntriesByCategory(categoryId)

getRelations(id)

getBacklinks(id)

resolveKnowledgeReference(id)

searchKnowledge(query)
```

以及类型：

```ts
KnowledgeEntry
KnowledgeRelation
ResolvedRelation
KnowledgeSearchResult
```

禁止外部：

```ts
import wood from './entries/wuxing/wood/entry'
```

正确方式：

```ts
import {
  getEntry
} from '@/knowledge/public-api'
```

# 17. URL 不属于知识核心

这一点需要和之前的初步方案稍作调整。

不建议让核心 API 提供：

```ts
getKnowledgeUrl()
```

因为：

```text
知识 ID
```

是知识本身的属性；

而：

```text
URL
```

属于前台。

独立知识库可能使用：

```text
/knowledge/wuxing/wood
```

未来龟甲可能使用：

```text
/kb/wuxing/wood
```

甚至可能直接跳到另一个域名。

因此：

```text
Knowledge Core
```

只负责返回：

```text
wuxing.wood
```

URL 由前台的：

```text
KnowledgeRouteAdapter
```

负责解析。

这样知识核心不会被某个网站的路由结构污染。


## Validator

```text

不存在的 relation target 会失败
```


而不需要在火中重复声明。

```text

```

可以解析。



## API

外部只通过：


# 23. v0.1 验收标准

满足下面所有条件才算底层架构通过：

1. 知识库脱离龟甲可以独立运行。
2. 删除龟甲项目不会影响知识库。
3. 新增知识条目不需要修改中央注册表。
4. 新增分类不需要修改页面业务判断。
5. 知识关系不需要双向重复录入。
6. 错误引用可以在开发阶段被发现。
7. 一个知识点可以拆成多个独立正文文件。
8. 前台不知道具体知识文件路径。
9. 所有外部消费者只通过 public API 读取知识。
10. URL 与 Knowledge ID 相互独立。
11. 五行五个条目可以互相建立关系和跳转。
12. 直接输入具体知识页地址能够正常访问。

# 24. 为未来龟甲保留的边界

未来龟甲只需要提供一个适配层。

例如：

```ts
const id = 'shishen.shangguan'

const entry = knowledgeApi.getEntry(id)
```

或者：

```text
排盘结果
伤官
 ↓
Knowledge ID
 ↓
前台 Route Adapter
 ↓
知识库详情
```

龟甲不应该知道：

```text
伤官文件在哪
正文是什么格式
关系如何建立
Markdown 如何读取
知识库内部目录是什么
```

因此未来知识库既可以：

```text
直接嵌入龟甲
```

也可以：

```text
作为共享 package
```

还可以：

```text
保持独立网站，由龟甲外链
```

当前阶段不提前决定。

## 最终原则

> 内容与程序分离。

> 一个文件尽量只承担一种职责。

> 一个知识事实尽量只维护一次。

> Knowledge ID 是跨系统稳定接口。

> URL、页面和视觉形式都不是知识本身。

> 测试阶段知识库完全独立存在。

> 龟甲未来可以使用知识库，但知识库不依赖龟甲。
